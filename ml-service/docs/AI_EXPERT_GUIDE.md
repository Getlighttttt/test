## 1. Что я нашёл, изучив файлы команды

### 1.1. Главный бэкенд — C# / ASP.NET Core 8 (WmsApi)
Подтверждено по коду `backend/WmsApi`: .NET 8, EF Core + Npgsql, cookie-сессии `wms_session`, роли `Skladnik` / `Dispecer`, порт `http://localhost:5134` (профиль `http`). Python гарантированно «iný jazyk».

Что из этого следует для ML-сервиса:
- в DB1 уже есть таблицы `Alert` (ProductId, LineName, RiskPercent, Message, Status NEW/ACK) и `ReplenishmentRequest` (Priority 1 = самый срочный, `AutoGenerated`) — **алерт ML сделан под эти поля**;
- материалы в DB1 — `MAT-001` (plech), `MAT-002` (skrutky), `MAT-003` (kábel) → симулятор ML использует **те же коды**, иначе C# не найдёт продукт;
- C# сам пишет историю в DB2, таблица `MovementLogs` (`MovementLogger`: RECEIVE, STORE, TO_LINE, QUARANTINE, QUARANTINE_REPAIR, WRITE_OFF…) → ML её **читает**, отдельные эндпоинты для событий не нужны;
- JSON у ASP.NET — camelCase → ML API тоже в camelCase.

### 1.2. docker-compose пока содержит только две базы
- `db1` → `wms_operational`, наружу порт **5433**
- `db2` → `wms_analytics`, наружу порт **5434**, пользователь `wms` / `wms123`

Важно: **внутри docker-сети** ML-сервис подключается к `db2:5432` (имя сервиса и внутренний порт), а **5434** — только когда запускаешь Python на ноутбуке без Docker. Это частая ошибка.

### 1.3. Количество контейнеров — обсудить с Architect
На картинке с критериями: «Docker **tri kontajnery alebo 4**». Сейчас выходит frontend + main-backend + ml-backend + db1 + db2 = **5**. А в описании проекта прямо написано «4 контейнера (frontend, main-backend, ml-backend, db-cluster)». Варианты:
- **(рекомендую)** одна PostgreSQL-контейнер `db` с **двумя отдельными базами** `wms_operational` и `wms_analytics` (создаются init-скриптом). Базы остаются сепаратными (разные БД, разные подключения), а контейнеров 4.
- оставить 5 и уточнить у преподавателя, что это допустимо.

Моему сервису всё равно — он берёт адрес из `DATABASE_URL`. Пример для варианта с одним контейнером — в разделе 13.3.

### 1.4. Дорожка «WMS & ML Systém» в BPMN = мой код
Именно эта часть Page-1 описывает работу ML-модуля, и код повторяет её один в один:

| Элемент BPMN (Page-1) | Где в коде |
|---|---|
| Priebežný zber dát o spotrebe materiálu na linke | `POST /api/telemetry` → таблица `consumption_log` |
| Odoslanie dát do Python ML modulu | вызов `service.process_telemetry()` |
| Výpočet predikcie nedostatku materiálu (ML Predikcia) | `registry.predict_risk()` |
| Шлюз **Riziko výpadku > kritická hranica?** | `risk >= settings.critical_threshold` (по умолчанию 0.70) |
| áno → Generovanie automatickej požiadavky na dopĺňanie | в алерте передаём `recommended_qty`; заявку в DB1 создаёт главный бэкенд |
| áno → Odoslanie notifikácie na TSD skladníka / Odoslanie výstrahy dispečerovi | `notifier.send_alert()` → `POST {main}/api/ml/alerts` |
| nie → Cyklický zber | ждём следующее измерение (в демо — `simulator.py`) |
| Zápis histórie presunov a predikcií do DB2 | `predictions` (ML) + `MovementLogs` (C#, событие `ML_ALERT`) |
| Kontrola alertov ML predikcie (Dispečer) | `GET /api/alerts`, `POST /api/alerts/{id}/ack` |
| Subproces 23: Odoslanie podkladov pre ML model (DB2) | C# пишет QUARANTINE / WRITE_OFF в `MovementLogs` → ML читает (`/api/analytics/defects`) |

### 1.5. Замечания для Domain Expert по BPMN (важно для 5 b BPMN)
Я посчитал элементы программно:
- **Подсчёт элементов в присланном `aispu_bpmn.drawio`:** задач (прямоугольники `task`) — Page-1: 40, Subproces 23: 13, **итого 53**; шлюзов — 8; событий — 10. **Все элементы потока вместе — 71.** Если «činnosť» = любой элемент потока, критерий 60 выполнен; если только задачи — не хватает 7. Уточните у преподавателя, как он считает. (Если у Domain Expert есть более новая версия, например `aispu_bpmn_3.drawio`, — пересчитать по ней.) Кандидаты на добавление из ML-части: «Príjem telemetrie», «Uloženie predikcie do DB2», «Kontrola duplicitného alertu», «Výpočet odporúčaného množstva», «Preučenie modelu», «Vyhodnotenie metrík modelu», «Nastavenie kritickej hranice».
- Оба события «Cyklický zber» нарисованы как **catching link**. У ветки «nie» должно быть **throwing** link-событие, а catching — там, где сбор начинается заново.
- «Zápis histórie presunov a predikcií do DB2» — **тупик** (нет исходящего потока и end-события). Плюс он стоит только на ветке «áno», а прогноз нужно записывать **всегда** (иначе не из чего считать качество модели). В коде я пишу в обоих случаях — лучше поправить схему: шлюз-слияние после обеих веток → запись в DB2.
- Subproces 23: у ветки «nie» шлюза «Je materiál opraviteľný?» нет целевого элемента; ещё одна стрелка висит без источника и цели; «Odoslanie reklamácie dodávateľovi» в дорожке WMS — без продолжения; в «Odpísanie materiálu zo stavu zásob**]**» лишняя скобка.

## 2. Архитектура

```
                     ┌───────────────────────────┐
  браузер            │ Frontend (React/Vue)      │
  TSD / дашборд ───▶ │  CRUD, логин   → main     │
                     │  прогнозы, KPI → ml (GET) │
                     └──────┬─────────────┬──────┘
                            │             │ GET /api/predictions/latest, /api/alerts, /api/analytics/*
                            ▼             ▼
┌────────────────────────────┐   ┌──────────────────────────────┐
│ Main backend (C#)          │──▶│ ML backend (Python/FastAPI)  │
│ сессии, роли, QR, заявки   │   │ - приём телеметрии/событий   │
│                            │◀──│ - ML прогноз риска дефицита  │
│ POST /api/ml/alerts        │   │ - алерты, метрики, обучение  │
└──────────┬─────────────────┘   └──────────────┬───────────────┘
           ▼   X-API-Key: события, телеметрия   ▼
        DB1 wms_operational              DB2 wms_analytics
   (users, роли, Product, Pallet,   C#  пишет: MovementLogs
    Alert, ReplenishmentRequest)     ML  пишет: consumption_log, predictions,
                                               model_metrics; читает MovementLogs
```

**Почему каждая таблица DB2 имеет одного «хозяина».** C# пишет только `MovementLogs`, ML — только свои три таблицы; читать чужое можно, писать — нет. Тогда изменение одной стороны не ломает другую, а обмен решениями (алерты, подтверждения, кнопки диспетчера) идёт через REST — это и есть «prepojenie aplikačných webových služieb».

**Ловушка EF `EnsureCreated()`.** Этот метод создаёт таблицы, только если в базе нет ни одной таблицы. Если ML стартует раньше C# и создаст свои таблицы, C# пропустил бы `MovementLogs` и упал на первой операции. Поэтому ML создаёт `MovementLogs` сам, в точности как EF (тот же DDL, `GENERATED BY DEFAULT AS IDENTITY`, `PK_MovementLogs`). Проверено на PostgreSQL 16 в обоих порядках запуска.

## Шаг 1. Окружение

```bash
cd ml-service
python -m venv .venv
# Windows: .venv\Scripts\activate     Linux/Mac: source .venv/bin/activate
pip install -r requirements.txt
```

**Почему версии закреплены (`==`).** Через месяц `pip install` без версий поставит что-то новее, и на компьютере преподавателя сборка может упасть. Я проверил именно этот набор версий в чистом окружении — все тесты прошли.

**Почему FastAPI, а не Flask.** FastAPI сам валидирует входящий JSON по Pydantic-схемам (неверный запрос → понятная ошибка 422, а не падение) и автоматически рисует документацию API на `/docs`. Эту страницу удобно показывать на защите и отдать C#-разработчику как спецификацию.

## Шаг 2. Конфигурация — `app/config.py`

Все параметры читаются из переменных окружения (или файла `.env`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | `…@localhost:5434/wms_analytics` | DB2. В Docker — `…@db2:5432/…` |
| `MAIN_BACKEND_URL` | `http://localhost:5134` | куда слать алерты (WmsApi) |
| `SERVICE_API_KEY` | `dev-ml-key` | общий секрет бэкендов |
| `CRITICAL_THRESHOLD` | `0.70` | **kritická hranica** из BPMN |
| `HORIZON_MINUTES` | `60` | «дефицит в ближайшие N минут» |
| `SIMULATOR_ENABLED` | `false` | включить имитацию линий |

**Почему через переменные окружения.** Один и тот же код работает на ноутбуке и в Docker — меняются только переменные в `docker-compose.yml`. Пароли и ключи не зашиты в код.

**Почему порог — параметр, а не число в коде.** Это бизнес-решение Domain Expert, а не программиста (см. роли в задании: «AI Expert настраивает порог срабатывания алертов (kritická hranica)»). Плюс его можно менять на лету: `PUT /api/model/threshold`.

## Шаг 3. Таблицы DB2 — `app/db.py`

| Таблица | Что хранит | Откуда данные |
|---|---|---|
| `consumption_log` | телеметрия с линии: запас, темп расхода, план, открытые заявки, время подвоза, **факт дефицита** (`shortage_occurred`) | `POST /api/telemetry` |
| `MovementLogs` | история операций — **пишет C#**, ML только читает (брак, TO_LINE для симулятора) | `MovementLogger` в WmsApi |
| `predictions` | каждый прогноз: риск, порог, критичен ли, рекомендованное кол-во, версия модели, отправлен ли алерт, подтвердил ли диспетчер | ML-сервис |

Таблицы создаются автоматически при старте (`Base.metadata.create_all`). Архитектору достаточно поднять пустую базу `wms_analytics` — схему ML-сервис создаст сам.

**Почему есть `shortage_occurred`.** Это «правильный ответ», который становится известен задним числом (см. шаг 7). Без него реальные данные нельзя использовать для обучения.

**Почему в `predictions` пишем и некритические прогнозы.** Чтобы на дашборде был график риска во времени и чтобы потом можно было посчитать, сколько тревог модель пропустила.

## Шаг 4. Постановка ML-задачи

**Вопрос, на который отвечает модель:** «Будет ли на линии X дефицит детали Y в ближайшие 60 минут?»

Это **бинарная классификация**: класс 1 = дефицит будет, класс 0 = не будет. Модель выдаёт **вероятность** класса 1 (`predict_proba`) — это и есть «процент риска», который сравнивается с kritická hranica.

**Почему классификация с вероятностью, а не регрессия «через сколько минут закончится».**
1. Шлюз в BPMN — это вопрос «да/нет», ему нужна вероятность, а не минуты.
2. «Время до нуля» (запас / темп) считается простой формулой — это мы тоже возвращаем (`minutes_to_stockout`) — но формула не знает, что заявка уже в пути, что AGV иногда опаздывает, что линия ускорилась. Модель учитывает всё это одновременно.

**Почему горизонт 60 минут.** Время подвоза со склада на линию — 10–45 минут. Если предупредить за 60, складник успевает. Слишком короткий горизонт → предупреждение приходит, когда уже поздно; слишком длинный → много ложных тревог.

## Шаг 5. Признаки — `app/ml/features.py`

Входные (то, что присылает линия):

| Признак | Смысл |
|---|---|
| `current_stock` | штук в медзискладе линии |
| `consumption_rate` | фактический расход, шт/ч |
| `planned_rate` | расход по такту, шт/ч |
| `open_requests` | есть ли уже заявка на пополнение |
| `lead_time_min` | типичное время подвоза |

Производные (считаем сами):

| Признак | Формула | Зачем |
|---|---|---|
| `coverage_min` | запас / темп × 60 | на сколько минут хватит |
| `slack_min` | coverage − lead_time | хватит ли, если заказать прямо сейчас |
| `rate_ratio` | факт / план | линия разогналась? |

**Почему производные признаки.** «120 штук» само по себе ничего не значит: при 30 шт/ч это 4 часа, при 240 шт/ч — 30 минут. Логист считает это в голове, и модели проще, если дать ей готовое. Результат видно в важности признаков: `coverage_min` ≈ 0.43, `slack_min` ≈ 0.27 — самые важные.

## Шаг 6. Данные: синтетика сейчас, реальные данные потом — `app/ml/synthetic.py`

**Проблема:** у учебного проекта нет месяцев истории с завода. Обучить модель «не на чем».

**Решение в два этапа:**
1. **Холодный старт.** Генерируем 6000 записей по упрощённой физике медзисклада: расход колеблется вокруг такта (иногда линия ускоряется на 20–50 %), подвоз приходит через lead time ± разброс, а в 12 % случаев сильно опаздывает («AGV застрял»). Метка = 1, если запас кончился раньше подвоза в пределах 60 минут.
2. **Обучение на своём заводе.** Когда в DB2 накопится ≥ 200 размеченных записей, `POST /api/model/train?source=auto` переобучает модель на реальных данных (шаг 7).

**Почему метка не равна простой формуле от признаков.** В симуляции есть случайность будущего (шум расхода, задержки транспорта), которую модель не видит. Поэтому модели есть чему учиться — она оценивает **вероятность**, а не повторяет правило. Это честнее, чем «модель с точностью 100 %».

**Как объяснить на защите:** «Синтетические данные — стандартный подход для холодного старта, когда исторических данных ещё нет. Архитектура уже готова к реальным данным: каждое измерение сохраняется в DB2, задним числом размечается, и модель переобучается».

## Шаг 7. Разметка истории из DB2 — `service.label_history()`

Каждое измерение в `consumption_log` старше 60 минут проверяется: было ли за следующие 60 минут по той же линии/SKU измерение с `current_stock <= 0`? Если да — `shortage_occurred = true`, иначе `false`.

**Почему так.** «Правильный ответ» на вопрос «будет ли дефицит через час» становится известен ровно через час. Это классическая схема обратной связи (feedback loop): модель предсказывает → жизнь показывает правду → модель учится на своих ошибках. Это сильный аргумент на защите, что ML здесь не «для галочки».

## Шаг 8. Обучение и выбор модели — `app/ml/model.py`

1. Делим данные 75 % / 25 % (`stratify` — чтобы доля дефицитов в обеих частях была одинаковой).
2. Обучаем **двух кандидатов**:
   - **LogisticRegression** (+ StandardScaler) — простой интерпретируемый baseline;
   - **RandomForestClassifier** (200 деревьев, max_depth=10) — ловит нелинейные комбинации («мало запаса **и** нет заявки» опасно, а по отдельности — нет).
3. Выбираем лучшего по **ROC AUC**, сохраняем в `models/shortage_model.joblib`, метрики — в `model_metrics`.

`class_weight="balanced"` — потому что дефицитов ~26 %, и без этого модель «ленится» и чаще говорит «всё хорошо».

**Почему ROC AUC для выбора.** Он оценивает, насколько хорошо модель **ранжирует** ситуации по риску, независимо от порога. Порог мы выбираем отдельно (шаг 9), так что сравнивать модели нужно без привязки к нему.

**Результат (тестовая выборка, 1500 записей):**

| Модель | ROC AUC |
|---|---|
| LogisticRegression | 0.990 |
| **RandomForest** (выбрана) | **0.992** |

Метрики RandomForest при пороге 0.5: accuracy 0.95, precision 0.87, recall 0.95, F1 0.91.

**Почему ModelRegistry с Lock.** Переобучение может идти одновременно с запросами на прогноз. Lock гарантирует, что запрос не попадёт на «полуподменённую» модель.

**Почему одни эндпоинты с ключом, а другие без.**
- **Чтение** (прогнозы, аналитика) открыто — фронтенд обращается к ML напрямую, это требование «frontend spojí oba backendy».
- **Запись и управление** требуют `X-API-Key`. Ключ знает только главный бэкенд. Секрет нельзя хранить во фронтенде (его видно в браузере), поэтому действия диспетчера (переобучить, сменить порог, подтвердить алерт) идут **через главный бэкенд**: он проверяет сессию и роль «Dispečer» и уже потом зовёт ML с ключом. Так роли и сессии остаются в одном месте — у Software Inžinier.

## Шаг 11. Алерты — `app/notifier.py` + `service.process_telemetry()`

Когда `risk >= hranica`, ML-сервис шлёт на главный бэкенд:

```http
POST http://localhost:5134/api/ml/alerts
X-API-Key: dev-ml-key
Content-Type: application/json

{
  "predictionId": 3,
  "productCode": "MAT-003",
  "lineName": "L2",
  "riskPercent": 91.4,
  "threshold": 0.7,
  "minutesToStockout": 53.4,
  "recommendedQty": 43,
  "priority": 1,
  "message": "Riziko výpadku MAT-003 na L2: 91 % (hranica 70 %). Doplniť 43 ks.",
  "modelVersion": "v20261025-133250-117",
  "createdAt": "2026-10-25T13:32:50.293169+00:00"
}
```
(это реальный запрос из моего тестового прогона)

Три продуманных момента:
1. **Кто создаёт заявку на пополнение.** Заявки, TSD и дашборд живут в DB1 у главного бэкенда. ML-сервис не лезет в чужую базу — он говорит «что, сколько и насколько срочно» (`priority` в шкале WmsApi), а главный бэкенд создаёт `Alert` и `ReplenishmentRequest(AutoGenerated=true)` и показывает её складнику и диспетчеру (три задачи BPMN после «áno»).
2. **Антиспам.** Если по этой линии/SKU уже есть неподтверждённый алерт за последние 10 минут, повторный не отправляется. Иначе при измерениях раз в 30 секунд диспетчер получал бы 20 одинаковых тревог. В живом тесте: 10 критических прогнозов → 3 алерта.
3. **Главный бэкенд упал — ML не падает.** Ошибка записывается в `predictions.alert_error`, а алерт всё равно доступен через `GET /api/alerts` (запасной pull-канал).

**Рекомендованное количество:** `max(факт, план) × (горизонт + время подвоза) / 60 × 1.2 − запас` — покрыть час работы плюс время в пути, с 20 % страховым запасом.

## Шаг 12. Симулятор линий — `app/simulator.py`

На защите нет настоящего конвейера. При `SIMULATOR_ENABLED=true` фоновый цикл каждые 30 секунд «прокручивает» 10 минут смены для 3 линий × 2 SKU: запас тает, считается риск, при критическом риске через пару тактов «приезжает» подвоз. Дашборд живёт сам, алерты появляются и исчезают.

**Почему это важно.** Без симулятора на защите пришлось бы вручную слать запросы. С ним преподаватель видит живую систему, а «Cyklický zber» из BPMN — буквально работающий цикл.

В продакшене симулятор выключается, данные шлёт линия или главный бэкенд через `POST /api/telemetry`.

## Шаг 13. Docker

### 13.1. `Dockerfile`
- база `python:3.12-slim` — маленький образ;
- сначала копируем `requirements.txt` и ставим зависимости, потом код — **слой с библиотеками кешируется**, и пересборка после правки кода занимает секунды, а не минуты;
- модель лежит в volume `/app/models` — не переобучается при каждом перезапуске;
- `HEALTHCHECK` на `/health` — Docker знает, когда сервис реально готов.

### 13.2. Блок для общего compose (отдать Architect) — `docker-compose.ml-snippet.yml`

```yaml
  ml-backend:
    build: ./ml-service
    container_name: wms-ml-backend
    depends_on: [db2]
    environment:
      DATABASE_URL: postgresql+psycopg://wms:wms123@db2:5432/wms_analytics
      MAIN_BACKEND_URL: http://main-backend:8080   # уточнить имя/порт у Software Inžinier
      SERVICE_API_KEY: ${SERVICE_API_KEY:-dev-ml-key}
      CRITICAL_THRESHOLD: "0.70"
      SIMULATOR_ENABLED: "true"
    ports: ["8000:8000"]
    volumes: [mlmodels:/app/models]
```

`depends_on` не ждёт, пока PostgreSQL реально примет соединения, поэтому при старте сервис сам **до 30 раз повторяет попытку подключения** (каждые 2 с). Это убирает классическую ошибку «первый `docker compose up` упал, второй сработал».

### 13.3. Если Architect сделает 4 контейнера (одна PostgreSQL, две базы)
```yaml
  db:
    image: postgres:16
    environment: { POSTGRES_USER: wms, POSTGRES_PASSWORD: wms123, POSTGRES_DB: wms_operational }
    volumes:
      - ./db/init:/docker-entrypoint-initdb.d   # там 01-create-analytics.sql: CREATE DATABASE wms_analytics;
```
и у ML-сервиса: `DATABASE_URL: postgresql+psycopg://wms:wms123@db:5432/wms_analytics`. Больше ничего менять не нужно.

## 18. Вопросы преподавателя — готовые ответы

**«Откуда данные для обучения?»** — Холодный старт на синтетике, построенной по физике медзисклада; каждое реальное измерение пишется в DB2, задним числом размечается (`label_history`), и `POST /api/model/train?source=auto` переобучает модель на реальных данных, когда их ≥ 200.

**«Почему Random Forest?»** — Сравнили с логистической регрессией по ROC AUC, лес чуть лучше и ловит нелинейные комбинации. Важность признаков показывает, что модель опирается на логичные вещи — запас по времени и наличие заявки.

**«Почему порог 0.7?»** — Компромисс между пропущенными дефицитами и ложными тревогами, выбран вместе с Domain Expert по таблице precision/recall. Меняется без перезапуска.

**«Зачем две базы?»** — DB1 — операционная (транзакции, быстрые записи складника), DB2 — аналитическая (история, обучение модели). Тяжёлые аналитические запросы и переобучение не тормозят работу склада. У каждой базы один владелец.

**«Что если главный бэкенд недоступен?»** — Прогноз всё равно сохраняется, ошибка доставки записывается, алерт доступен через `GET /api/alerts`.

**«Как защищено API?»** — Запись и управление — только с `X-API-Key` (знает только главный бэкенд); пользовательские роли и сессии проверяет главный бэкенд, прежде чем проксировать действие диспетчера.
